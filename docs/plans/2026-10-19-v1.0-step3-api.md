# v1.0 step 3: API and tokens — implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to
> implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** a JSON API under `/api/v1`, authenticated by scoped bearer tokens, exposes swipe sessions, items, ask, search, follows, feeds,
settings and runs to the Android app; tokens are created by a CLI command or by pairing a phone with a QR code on `/ui/setup`; an OpenAPI
document and JSON contract fixtures fix the shapes the app codes against.

**Architecture:** a new `Api` folder holds the endpoint group, a bearer-token endpoint filter and request/response records. Handlers call the
existing services; three services are reshaped so they return data instead of Telegram HTML (archive ask, item ask, item full text), and
Telegram renders that data exactly as before. Swipe gains a "peek" read so the app can fetch cards ahead without marking them shown.

**Tech stack:** .NET 10 minimal APIs, ASP.NET Core rate limiting and ProblemDetails (shared framework), `Microsoft.AspNetCore.OpenApi` (new
package), `QRCoder` (new package, MIT) for the pairing QR as SVG, Dapper/Npgsql, xUnit + Testcontainers + `WebApplicationFactory`.

**Spec:** `docs/specs/2026-10-19-v1.0-app.md` (Server 4). Master plan: `docs/plans/2026-10-19-v1.0-app.md` (step 3).

## Global constraints
- `/ui`, `/swipe` and `/mcp` keep their auth rules unchanged; `Mcp:Token` never authenticates `/api/v1`.
- `/api/v1` accepts only `Authorization: Bearer <token>` of an unrevoked token with scope `app`; any `Origin` header is refused (403), so a browser page can never call it; no CORS.
- Only a SHA-256 hash of a token is stored; the plain token is shown exactly once (CLI output or the pairing page) and never logged.
- Errors are RFC 7807 problem details (`application/problem+json`); 64 KB request body limit; a per-token rate limit.
- An instance with no tokens behaves as today (the group answers 401; nothing else changes).
- Migration `0031_api_tokens.sql`; new tables go into `PostgresFixture.ResetAsync`; add `0031` to `CombinationTests`' migration lists.
- Endpoint test classes share one app host per class (as `SwipeStackTests` does) to stay under the test Postgres connection limit.
- `dotnet test FeedEater.slnx` (Docker; outside the Bash sandbox) and `dotnet format --verify-no-changes` before each commit.

## Decisions taken in this plan (rulings, recorded)
- **R-f. Two new packages:** `Microsoft.AspNetCore.OpenApi` (first-party .NET 10 OpenAPI generator) and `QRCoder` (MIT, no native deps) for the pairing SVG. Writing either by hand is the larger risk. Cost if wrong: two dependencies to keep pinned.
- **R-g. Settings are what is runtime-settable today:** the manual quiet switch (`QuietHours.SetAsync`) and the learn switch (`TasteSwitch.SetAsync`). The quiet window and digest time are returned read-only (config). Notification kinds arrive with step 5 (push).
- **R-h. Feed add/remove only on the built-in reader.** With `Source:Kind=miniflux` they answer 409 "Add or remove feeds in Miniflux"; list and mute work in both modes (as `/ui/sources` today).
- **R-i. Follow start is part of the API** (`POST /follows {itemId}`); the spec's list omitted it, but the Reader's Follow button needs it.
- **R-j. Fetch-ahead is a peek.** `POST /swipe/next {position, peek: true}` returns the card at that position (within the cap) without raising `cards_shown` and without counting an inbox showing; the first `/swipe/event` for a position counts it as shown. A peek never starts, expires or ends a session.
- **R-k. Base URL in the pairing QR:** `FeedEater:Api:BaseUrl` when set, else the request's scheme and host.
- **R-l. Version** comes from the assembly's informational version (the Dockerfile's `-p:Version`), else `"dev"`.

## Review focus
1. **A browser page calling the API.** Any request with an `Origin` header → 403, even with a valid token. Task 2.
2. **Revoked or unknown token, wrong scheme, two spaces, lowercase `bearer`.** All 401 with a problem body that does not echo the token. Task 2.
3. **A peeked card acted on.** An event on a peeked position counts it as shown once; then acts work; a peek past the cap returns the summary without ending the session. Task 3.
4. **Miniflux mode.** Feed add/remove → 409 problem, not 500; list works. Task 5.
5. **Telegram output unchanged** after ask and item-ask are reshaped: the same HTML for the same model answer. Task 4.

### Task 2: the API group, auth filter, limits, problems, OpenAPI, status

**Interfaces produced:**
- `public static RouteGroupBuilder MapFeedEaterApi(this IEndpointRouteBuilder app)` in `ApiEndpoints.cs`, mapped in `Program.cs` after `MapFeedEaterUi()`; later tasks add their routes to the returned group (one `Map…Api(group)` method per task area).
- `ApiAuth` endpoint filter; on success `HttpContext.Items["api-token"]` holds the `ApiTokenRow`.
- `SwipeService.GateAsync(CancellationToken) → Decision` — the same `SessionPolicy.Decide` call `NextAsync` makes, read-only (no expire, no start).
- `GET /api/v1/status → StatusResponse`:

```csharp
public sealed record StatusResponse(string Version, string Gate, DateTimeOffset? GateUntil, string? GateWhy, DigestStatus? Digest, bool Telegram, bool Swipe);
public sealed record DigestStatus(string Date, string Status, int Items, DateTimeOffset? SentAt);
```

`Gate` maps `Gate.Resume | Gate.Expire | Gate.Start` → `"open"`, `Gate.Summary` → `"summary"`, `Gate.Closed` → `"closed"`; with swipe off → `"off"`.

Behaviour:
- Filter order: `Origin` header present → 403 problem "Browsers may not call the API"; `Authorization` not exactly `Bearer <token>` (case-sensitive scheme, one space) → 401 problem "A bearer token is required"; `VerifyAsync` null or scopes without `app` → 401 problem "Token not accepted". No problem body contains the token.
- Rate limit: `AddRateLimiter` with a fixed window, 120 requests a minute per token id (taken from the `Authorization` header's hash before the filter runs, so unknown tokens share one partition of 20 a minute); rejection → 429 problem.
- Body limit: the group carries `RequestSizeLimitAttribute(65_536)` metadata; larger → 413.
- `AddProblemDetails()`; an unhandled exception inside the group → 500 problem without exception text (an exception filter or `UseExceptionHandler` scoped by path).
- OpenAPI: `AddOpenApi("v1")`; `app.MapOpenApi("/api/v1/openapi.json")` outside the auth filter (metadata only, no secrets); group routes carry `.WithName(...)` and `.Produces<T>()`.

### Task 3: swipe over the API, with peek

**Interfaces:** consumes `SwipeService`; produces `SwipeService.PeekAsync(int position, CancellationToken) → NextResult`; `EventAsync` counts a position as shown.

Routes (bodies are the `/swipe` records without `Csrf`, as new records in `ApiModels.cs`; responses are the same JSON types):
`POST /api/v1/swipe/next {position?, peek?}`, `/act {session, position, act, clientId}`, `/undo {session, position, clientId}`, `/event {session, position, shownAt, dwellMs, direction}`, `/felt {session, felt}`, `/end {session}`.

Behaviour (ruling R-j):
- `peek: true` → `PeekAsync(position)`: decides the gate like `NextAsync` but never starts, expires or ends a session. No open session → the result `NextAsync` would return for that gate without starting one (summary in the summary window, else closed with the gate's reason; `Gate.Start` → `closed` with why `"not-started"`). Open session → the card at `position` built exactly as `CardAsync` builds it but **without** `RaiseShownAsync` and without `InboxStore.MarkShownAsync`; a position at or past `min(CardCap, queue length)` → the session's summary view without ending it. Refactor the card building into one method with a `markShown` flag; no duplicated view code.
- `EventAsync` for a position `>= CardsShown` that is inside the queue and cap: raise `cards_shown` to `position + 1` and, for an inbox card, call `MarkShownAsync`, then record the event as today. `ActAsync`/`UndoAsync` keep requiring a shown position.
- The `/swipe` routes (PWA) are unchanged.

# v1.0 app: master plan

> **For agentic workers:** this file orders the seven PRs and fixes the interfaces between them. Each step gets its own detailed plan
> (`docs/plans/2026-10-19-v1.0-stepN-*.md`) written against `main` as it is when the step starts; only step 1's exists now. Implement a detailed
> plan with superpowers:subagent-driven-development or superpowers:executing-plans; steps use `- [ ]`.

**Goal:** an Android app on top of swipe mode replaces the Telegram bot (spec: `docs/specs/2026-10-19-v1.0-app.md`).

**Architecture:** the jobs that message the owner write to an `inbox` table. A swipe session's queue gets fixed slots for the digest and inbox
entries ahead of recall, seeds and ranked items. Acts become idempotent by a client id. A token-authenticated `/api/v1` exposes the same
services to a Compose app, and saved items go to a library inside feed-eater.

**Tech stack:** .NET 10, ASP.NET Core minimal APIs, Dapper + Npgsql on Postgres 18 with pgvector, xUnit + Testcontainers + `WebApplicationFactory`;
Android: Kotlin, Compose, Material 3, Hilt, Navigation, kotlinx.serialization, OkHttp, Room, WorkManager, minSdk 31.

**Spec:** `docs/specs/2026-10-19-v1.0-app.md`.

## Global constraints
- Every integration stays optional. An instance with neither Telegram nor the app configured behaves as `main` does today.
- While `Telegram:Token` is set, every message the bot sends today is still sent, with the same text and buttons, until step 7 removes it on the owner's side.
- `/swipe`, `/ui` and `/mcp` keep their auth rules (cookie, csrf body field, same-origin check, `Mcp:Token`). `/api/v1` uses bearer tokens only.
- Swipe mode's guards stay: dwell never feeds ranking; the swipe path calls no LLM.
- Migrations continue at `0029`, one file per step that needs one, applied in name order by `DatabaseMigrator`.
- Every new table goes into `PostgresFixture.ResetAsync`'s truncate list.
- `OwnerTermsTests` stays green; from step 6 it also scans `android/`.
- Tests: `dotnet test FeedEater.slnx` (Docker needed); `dotnet format --verify-no-changes` clean. Android: `./gradlew test connectedCheck` where a device exists, else `test` + screenshot tests.
- Comments: few, and only about why.

## Review focus (failure modes no single step's tests cover)
1. **A retried request doubles a side effect.** The phone resends an act after a timeout: one vote, one library row, one Plane item. Owned by step 2 (`swipe_acts`); step 3's API tests repeat it over HTTP; step 6's outbox test repeats it from the app.
2. **Telegram off half-way.** With `Telegram:Token` empty, every job still produces its inbox entry and no job fails or deletes state (a follow without a root message, a duel marked failed). Owned by step 1 (per job), checked again in step 7's parity pass.
3. **The cap hides the digest.** More digest plus inbox entries than `Swipe:Cards`: the rest must carry into the next session, not vanish or expire early. Owned by step 2.
4. **A long offline day.** The session's time cap passes while the phone is offline with queued acts: the acts still land on the positions they were made on. Owned by step 2 (acts accepted on an expired session up to 24 h) and step 6.
5. **Hostile feed text in new card kinds.** Release notes, follow items and idea text come from the internet: the PWA renders them with `textContent`, the app as plain text, links only `http(s)`. Owned by steps 2 (PWA) and 6 (app).

## Steps

### Step 1 — Inbox (detailed plan: `2026-10-19-v1.0-step1-inbox.md`)
Produces `IInbox.AddAsync(InboxEntry, OutMessage, ct, replyTo?) → InboxPost(Id, TelegramMessageId?)`, `InboxStore` (`OpenAsync`, `DoneAsync`,
`GetAsync`), table `inbox`, idea staging with Keep/Drop (`IdeaDecisions.KeepAsync/DropAsync`), and jobs gated on "Telegram or Swipe".

### Step 2 — One stack (detailed plan: `2026-10-19-v1.0-step2-stack.md`)
Consumes `InboxStore.OpenAsync(now, limit)` and `DigestStore` (latest digest's `item_ids`).
- `BuildQueueAsync`: unshuffled head `notice → digest → inbox`, then the existing shuffled tail; `QueuedCard.Kind` gains the new kinds, `Id` = inbox id for inbox kinds.
- `CardView.Detail` per kind; `ActAsync` per the spec's act table, calling `IdeaDecisions`, `StoryFollower.CloseAsync`, `DuelStore.AnswerAsync`, release mute, `InboxStore.DoneAsync`.
- `swipe_acts(client_id uuid pk, session_id, position, act, at, previous_vote smallint null, undone_at null)`; `ActAsync(…, Guid clientId)` returns the stored result on a repeat; `UndoAsync(session, position, clientId)`.
- Acts accepted for an ended session for 24 h (offline phone).
- A `notice` entry for feeds that failed 3 times in a row (today only named in the digest header), keyed `notice:feeds:{date}`.
- `DigestJob` runs without Telegram when Swipe is on: `DigestRun` stores the selection and marks it `sent` without sending (step 2 plan, ruling R-a: no new `ready` state).
- PWA: `swipe.js` sends `clientId` (`crypto.randomUUID()`), renders the new kinds with `textContent`, offers Undo.
Produces: `SwipeService.NextAsync(position)`, `ActAsync(session, position, act, clientId)`, `UndoAsync(…)` used by step 3 unchanged.

### Step 3 — API and tokens (detailed plan: `2026-10-19-v1.0-step3-api.md`)
- `api_tokens`, `ApiTokenStore`, `BearerAuth` endpoint filter (scope `app`), rate limit per token, 64 KB body limit, problem details.
- `/api/v1` group: swipe (incl. fetch-ahead: `next` with a position does not mark later cards shown), items, ask, search, follows, feeds, settings, digest run, status.
- `/ui/setup` "Pair a phone": QR (SVG rendered server-side, no script, CSP unchanged) with `{baseUrl, token}`, token list with revoke; `token create` CLI.
- OpenAPI document; `tests/contract/*.json` fixtures written by the API tests.
Produces: the OpenAPI document and fixtures step 6 codes against.

### Step 4 — Library
- Migration: `saved.karakeep_id` nullable, `source`, `read_at`, `note`.
- `LibraryService.SaveAsync(itemId|url, source, ct)`: create item for a new URL, fetch full text once via `SafeFetcher`, read + embed when missing, vote +1 weight 1, optional Karakeep mirror; replaces Karakeep calls in `SwipeService.SaveAsync` and `CallbackHandler`.
- `/api/v1/library*`; `resurface` inbox entries weekly (max 3); `feed_search` gains `saved`.
- `Karakeep:Mirror` option; one-time `import-karakeep` command.

### Step 5 — Push and doctor
- `Push:NtfyUrl|Topic|Token`; `PushNotifier` posts one message after the digest is ready ("Today: N cards", click `feedeater://stack`), held by quiet hours, per-kind opt-in from settings; at most one retry an hour.
- `doctor`: push line, token list with last use, Telegram `off` when the token is empty.

### Step 6 — Android app, core
- `android/` Gradle project (`io.github.feed_eater`), CI job building and testing it.
- Pairing (QR, EncryptedSharedPreferences, HTTPS only), Stack (gestures, labels, haptics, Undo, buttons, TalkBack actions, every kind, summary + felt, closed view), Reader, Room cache, outbox + WorkManager sync, offline bar, deep link.
- Contract tests parse `tests/contract/*.json`.

### Step 7 — Android app, rest, and release
- Library, Search & Ask, Follows, Feeds, Settings (incl. Run digest now, Run ideas now), share sheet (Save / Add as feed).
- Signed APK on tag `app-v*` attached to the GitHub release.
- Parity pass: every row of the spec's table exercised on a phone; risk review by a second agent; release v1.0.
- Owner side (homelab-gitops PRs, owner merges): HTTPS tailnet name, `Swipe:Enabled`, `Push:*`, then `Telegram:Token` removed.

## Order and parallelism
1 → 2 → 3 are sequential (each consumes the previous one's interfaces). 4 and 5 can run in parallel after 3. 6 can start after 3 (it needs
only the API and fixtures) and run alongside 4 and 5; 7 needs 4, 5 and 6.

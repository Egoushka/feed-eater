# v1.0: the app

Goal: a native Android app becomes the way to use feed-eater, and Telegram goes. The app is a client of the swipe mode that is already built
(`docs/specs/2026-10-16-swipe-mode.md`, PRs #13 to #15): one capped stack a sitting, in which the day's digest comes first and everything the bot used
to send arrives as a card. Saved things go to feed-eater's own library, with AI on it, instead of Karakeep. One quiet notification a day.
Tailnet only.

Decided with the owner 2026-10-19:
- Android, Kotlin, native, in `android/` of this repository. Same stack as the owner's other Android apps: Compose, Material 3, Hilt,
  Navigation, kotlinx.serialization, coroutines, WorkManager, Room, minSdk 31. Swipe mode's D1 named "a native app" as the reason that would
  justify a client outside the PWA; this is that.
- **One stack.** The digest's items become the first slots of a swipe session; follow updates, duels, release alerts, ideas, the weekly review,
  the autopsy and notices become new slot kinds. One ranking, one cap, one event log.
- **Swipe mode's gestures stay:** up = next (neutral), right = save, left = dislike, down = back, double-tap = like; every action also a button.
- **The `/swipe` PWA stays**, served by the same service, for desktop and for an instance without the app.
- **Telegram goes with full parity in v1.0:** the owner's deployment drops `Telegram:Token` on release day. The bot code stays as an optional
  channel for other instances.
- **Saving goes to feed-eater's own library**, with AI on it; Karakeep becomes an optional mirror.
- Reachable on the tailnet only.

Facts this rests on (read from `origin/main` f1ed88c, 2026-10-19):
- Swipe mode is live and unused: 0 rows in `swipe_sessions`, `swipe_events`, `recall_cards` and `categories` on the owner's instance
  (2026-10-19). The owner did not know it was live.
- Swipe routes (`Swipe/SwipeEndpoints.cs`): `POST /swipe/next {csrf, position?}`, `/swipe/act {csrf, session, position, act}`,
  `/swipe/event {csrf, session, position, shownAt, dwellMs, direction}`, `/swipe/felt {csrf, session, felt}`, `/swipe/end {csrf, session}`. Auth is
  the `fe_session` cookie from `/ui/login`, a `csrf` body field, and a same-origin check (`Ui/UiEndpoints.cs:12`); 503 without `Mcp:Token`; mapped only
  with `Swipe:Enabled`. Responses are `NextResult(Type card|summary|closed, CardView?, SummaryView?, ClosedView?)` (`Swipe/SwipeService.cs:9-20`).
- The queue is fixed at session start (`SwipeService.BuildQueueAsync`, `SwipeService.cs:142`): due recall cards, new seeds, then ranked items from
  `SwipeQueue.Build`, all shuffled together. Slots are `QueuedCard(Id, Category, Source, Predicted, Kind)` with kind `item | recall | seed`, stored as
  parallel arrays on `swipe_sessions`. Caps (`SwipeOptions`, `FeedEaterOptions.cs:184`): 40 cards, 15 minutes, 180 minutes cooldown, 3 sessions a day.
- Acts (`SwipeService.ActAsync`, line 192): item `idea save share like dislike open`; recall `good again`; seed `send dismiss`. Like/dislike write
  `votes` at weight 0.5; save writes a vote at weight 1 then calls Karakeep through the Telegram callback handler. Next and back are the `direction`
  of `/event`, not acts. **No idempotency for acts:** a repeated `/act` repeats the vote and the Karakeep call; `/event` is an upsert on
  `(session_id, position)`.
- The digest (`Digest/DigestRun.cs:20-74`) stores its selection as `digests.item_ids` and sends one Telegram message per item; items load as
  `DigestItem(Id, Title, Url, Feed, Project, Kind, Summary, Why, Suggestion, AlsoIn)`.
- Everything else that reaches the owner calls the concrete `TelegramClient.SendAsync(chat, OutMessage, ct)`: `DigestJob` (lines 75, 88),
  `DuelJob:51`, `StoryFollower:60,92,118`, `ReleaseWatcher:117`, `WeeklyReview:34`, `AutopsyJob:35`, `WeeklyIdeas/WeeklyIdeasJob:118`. There is no
  interface in between.
- Commands and replies (`Telegram/CommandHandler.cs`, `ReplyHandler.cs`): `/ask /digest /feeds /follows /ideas /learn /quiet /search /unfollow`; a
  free-text reply to an item becomes a vote, idea, save, feed mute or an answer about the item.
- No JSON API, token table, OpenAPI document or push code exists. `Mcp:Token` is the only credential.
- `saved(item_id, karakeep_id not null, at)` (migration 0007). Next free migration number: 0029.
- Tests: `dotnet test FeedEater.slnx`, `WebApplicationFactory<Program>` over Testcontainers Postgres (`PostgresFixture`), as in `SwipeEndpointTests`.
- LLM spend is about $0.08 a day in total (14 days to 2026-10-18: $1.13).

## Server

### 1. Inbox: what used to be a Telegram message
New table `inbox(id, kind, item_id null, ref_id null, payload jsonb, created_at, expires_at null, shown_session null, done_at null)`.
Kinds: `follow` (a new item in a followed story), `duel`, `release`, `idea`, `review`, `autopsy`, `resurface` (section 5), `notice` ("no digest today:
…", feeds failing three times). The jobs listed above stop calling `TelegramClient` and call `IInbox.AddAsync(InboxEntry)`. A `TelegramInboxSender` renders each new
entry the way the job's message looks today, only while `Telegram:Token` is set, so the bot behaves as now during the move and on other instances.

`idea`: `WeeklyIdeasJob` stops filing in Plane on its own. It adds one `idea` entry per shortlisted idea; **keep** files it through the existing
`IIdeaSink` and records `weekly_ideas`, **drop** records it as dropped so the next run does not offer it again. Ideas only reach Plane after a swipe.
(Telegram, while still on, gets Keep and Drop buttons for the same entry.)

### 2. One stack
`BuildQueueAsync` gains two sources ahead of the existing ones, in this order, and these are **not shuffled**:
1. `notice` entries.
2. `digest`: the latest digest's `item_ids` that have no vote yet and were not shown in an earlier session, kind `digest`, source `digest`.
3. Open inbox entries (follow, duel, idea, release, review, autopsy, resurface), oldest first, kind = the entry kind, `Id` = inbox id.

Then due recall, seeds and ranked items exactly as now (still shuffled among themselves). The card cap still applies; when digest plus inbox exceed
it, the rest waits for the next session. An inbox entry shown and left with `next` stays open for one more session, then expires
(`done_at`). Entries past `expires_at` are not queued (follow: 7 days, release: 14, others: 7).

`CardView` gains `Kind` values `digest | follow | duel | release | idea | review | autopsy | resurface | notice` and an optional `Detail` object per kind
(duel: both items; release: package, from, to, verdict; idea: title, project, source; review and autopsy: the text; follow: story title).
`digest` cards carry `Summary` and `Suggestion` from the digest read.

Acts per kind (the swipe gestures map onto them as for `item`; anything without a gesture is a button):

| kind | right | left | double-tap | buttons |
|---|---|---|---|---|
| `item`, `digest` | save | dislike | like | idea, share, open, like, dislike, save |
| `follow` | save | stop (ends the follow) | like | open, stop |
| `duel` | — | — | — | pick A, pick B (next = skip) |
| `release` | — | mute package | — | open notes, mute |
| `idea` | keep | drop | — | open source, keep, drop |
| `resurface` | keep (stays saved) | remove from library | — | open, mark read |
| `review`, `autopsy`, `notice` | — | — | — | open |
| `recall`, `seed` | as now | as now | — | as now |

### 3. Acts become idempotent, and undoable
New table `swipe_acts(client_id uuid primary key, session_id, position, act, at, undone_at null)`. Every act (from the API and from the PWA, which
gets a `crypto.randomUUID()`) carries a `clientId`; a repeated `clientId` returns the first result and runs no side effect. `POST …/undo
{session, position, clientId}` reverses the act with that id within 24 hours: vote restored to what it was before (the previous value is stored on
the row), save removed from the library, follow restarted, idea keep or drop reopened (only if Plane filing failed or has not happened; a filed
Plane item is not deleted, the answer says so). Down-swipe "back" stays what it is: navigation.

### 4. API for the app (`/api/v1`, JSON, bearer token)
Thin endpoints over the same services; no logic in handlers. Errors are RFC 7807 problem details; OpenAPI at `/api/v1/openapi.json`.

- Swipe: `POST /swipe/next {position?}`, `/swipe/act {session, position, act, clientId}`, `/swipe/undo {session, position, clientId}`,
  `/swipe/event {…}`, `/swipe/felt {…}`, `/swipe/end {session}` — same bodies as the cookie routes minus `csrf`, same `NextResult`.
- Items: `GET /items/{id}` (full text: stored text, else fetched once through `SafeFetcher`; summary, why, suggestion, feed, vote, saved),
  `POST /items/{id}/ask {question}`.
- `POST /ask {question}` (the `/ask` answer with checked citations), `GET /search?q=&kind=&project=&from=&to=&saved=`.
- Library: `POST /library {url, title?, text?}`, `GET /library?state=unread|read|all&after=`, `POST /library/{itemId}/read`,
  `DELETE /library/{itemId}`.
- `GET /follows`, `DELETE /follows/{id}`; `GET /feeds` (👍 rate, failures), `POST /feeds {url}`, `POST /feeds/{id}/mute`, `DELETE /feeds/{id}`.
- `GET /settings`, `PUT /settings`: quiet hours, the learn switch, digest time, which inbox kinds may notify.
- `POST /digest/run`.
- `GET /status`: server version, whether the gate is open (and until when), today's digest state. The app's first call.

Authentication: table `api_tokens(id, name, hash, scopes, created_at, last_used_at, revoked_at)`; only a SHA-256 hash is stored and the token is
shown once. Scope `app` covers all of `/api/v1`. `/ui/setup` gets **Pair a phone**: a QR code with `{baseUrl, token}` and a list of tokens with
revoke. Rate limit per token, 64 KB bodies, no CORS. `Mcp:Token` keeps working for `/mcp`, `/ui` and `/swipe`, which keep their cookie, csrf
and same-origin rules unchanged.

### 5. Library (own save, with AI)
`saved` changes: `karakeep_id` becomes nullable; new columns `source` (`swipe`, `share`, `import`), `read_at`, `note`. One `LibraryService.SaveAsync`
replaces the Karakeep call in `SwipeService.SaveAsync` and in the Telegram callback.

When something is saved:
1. A new URL (`POST /library`) becomes an item with no feed, `source_key = share:<canonical url>`, deduplicated by canonical URL like any item.
2. Full text is fetched once through `SafeFetcher` and stored, so it reads offline and is searchable. A 403 or paywall keeps the shared text and
   marks the item "no full text".
3. With no read yet, the read model writes summary and why against the profile, and the item is embedded. One read call per save.
4. It counts as a like at weight 1, as a save does today, so it teaches the ranking and creates recall cards as liked items already do.
5. `Karakeep:Mirror` (default false) also copies it to Karakeep. Karakeep bookmark import stays as an optional one-time import.

Saved items unread for 14 days come back as `resurface` inbox entries, at most 3 a week (keep / remove). `feed_search` in MCP gets `saved`. Text
notes are not supported: the library holds links and articles.

### 6. Push
`Push:NtfyUrl`, `Push:Topic`, `Push:Token` (optional). One message a day after the digest run: "Today: 9 cards", click `feedeater://stack`.
An inbox kind notifies on its own only if Settings allows it (default: none). Quiet hours hold every message. No push settings, no push.

### 7. Doctor
Checks the push target (`ok`, `off`, `FAIL` with the fix) and lists API tokens with their last use. With `Telegram:Token` empty, Telegram is `off`.

## App (`android/`)
Package `io.github.feed_eater`, one `app` module. Layers: `api` (OkHttp + kotlinx.serialization, models matching the OpenAPI document), `data`
(Room: current session, cards, items, library, outbox), `ui` (Compose screens and ViewModels), `work` (WorkManager sync).

- **Pairing.** Scan the QR from `/ui/setup`; the token lives in EncryptedSharedPreferences. HTTPS only, no cleartext exception (the app names no
  host); the deployment serves feed-eater on an HTTPS name reachable only on its private network.
- **Stack.** One card a screen, the next one peeking. Gestures as decided; the action's label shows while dragging; haptics; Undo after every act.
  Every act is also a button and a TalkBack custom action. Kind-specific layouts for the table above. The summary card with the "how did this leave
  me" tap; the closed view says until when, and offers Library and Search meanwhile.
- **Reader.** Full text, summary, why, suggestion; Ask about this; Follow; Mute feed; Note.
- **Library.** Unread / Read, search inside, swipe to mark read or remove.
- **Search & Ask.** One box: a question goes to `/ask`, other text to search.
- **Follows, Feeds, Settings.** As the API.
- **Share sheet.** Accepts `text/plain` links: **Save to library** or **Add as feed**.
- **Offline.** The session's queue is fixed on the server, so the app fetches cards ahead (up to 10) and caches them; acts and events go into an
  outbox sent in order by WorkManager with backoff, each with its `clientId`. Without a sync for 15 minutes a grey bar says "offline, last synced …".
- Deep link `feedeater://stack`. Release: CI builds a signed APK on tag `app-v*` and attaches it to the GitHub release.

To fetch ahead, `POST /api/v1/swipe/next` accepts `{position}` for any position below the cap, without marking later cards shown until an event
for them arrives. (The PWA keeps fetching one at a time.)

## Errors
- Server or tailnet gone: cached cards keep working, acts queue, the grey bar shows it.
- Token revoked: 401 sends the app to Pairing; the outbox is kept and sent after pairing.
- Act on a card whose session ended, or a repeated `clientId`: the first result is returned, no error shown.
- Gate closed: the closed view with the time it opens; Library and Search still work.
- Push target down: the digest still runs; doctor and `/ui` show it; at most one retry an hour.

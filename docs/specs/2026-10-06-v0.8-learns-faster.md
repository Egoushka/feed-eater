# v0.8: learns faster

Goal: close the loop between what you read, what you do and what the ranking learns. Today there are 10 👍 and 1 👎 against the 100 votes
(10 of each kind) the learned ranking needs, so the first four features exist to produce signal and the last two to show what the ranking
learned. Every feature is off or inert until its inputs exist and costs cents per month.

Facts this rests on (audit of v0.7 branch, 2026-10-06; file:line at `feat/v0.7`):
- `votes` is one row per item, `value smallint check in (-1,1)` (`0001_init.sql:70-74`); `SetVoteAsync` overwrites, `ClearVoteAsync`
  deletes (`FeedbackStore.cs:46-70`). No weight anywhere: `LabeledVector(X, Liked)` (`LogisticModel.cs:5`), `Positive/NegativeVectorsAsync`
  return bare `float[]` lists, `Vectors.Centroid` is unweighted, `FeedVotesAsync` counts.
- `ideas.plane_issue_id` holds what `CreateIntakeAsync` returned (`PlaneClient.cs:52-60`); `LocalIdeaSink` stores `""`. `PlaneClient` reads only
  names and states, one page of 100, and has no comment call.
- `ScheduledJob` has one `DueKey` per tick and fires once per key (`Loops/ScheduledJob.cs`); `Schedule` offers daily/weekly keys only.
- Telegram: `SendAsync` has no `reply_to_message_id`; a reply to a message whose buttons name an item is treated as a command on that item
  (`TelegramClient.cs:83-103`, `ReplyHandler`).
- UI: server-rendered strings, one stylesheet, CSP `default-src 'none'; style-src 'self'` (`UiEndpoints.cs:32-33`): no scripts, no images, no
  inline `style=`; inline `<svg>` elements with presentation attributes are allowed. No dimensionality reduction exists.
- GitHub client is unauthenticated (60 requests/hour, `GitHubStarsClient.cs:8`), returns stars, pushed_at, latest release.

## Foundation W: vote weight
Migration 0012: `votes.weight real not null default 1 check (weight > 0 and weight <= 3)`. `value` stays ±1. Every reader uses it:
`LabeledVector` gains `Weight`; `LogisticModel.Train` multiplies each example's gradient by its weight (class balance counts weight, not
rows); centroids become weighted means; `FeedVotesAsync` sums weights; `LearnedTaste.Prepare`'s vote counts (the 100/10 floors) count rows,
not weights, so a weighted vote never lets the floor be reached early. The web UI and Telegram buttons keep writing weight 1.
`SetVoteAsync(itemId, value, weight = 1)`; a later manual vote overwrites weight too (your own vote always wins).

## F1. Duel
Twice a day (default 12:30 and 20:30 local, `Duel:Times`), two unvoted items arrive in one message with buttons `◀ first` `second ▶` `skip`.
- **Pick:** unvoted, embedded, unmuted items published in the last 7 days, one per story, triaged relevance >= 1 (so they have a score). From
  the middle band (score between the 40th and 60th percentile of that pool, where the ranking is least sure), take the pair with the lowest cosine
  similarity (different topics). Fewer than 6 eligible items: no duel that time.
- **Result:** winner → 👍 weight 1; loser → 👎 weight 0.5 (a loser is not a disliked item). `skip` writes nothing and the pair is not offered
  again. An item that already has a vote keeps it. New table `duels(id, a, b, sent_at, winner, answered_at)`; the message edits to
  "You picked X" after the tap.
- **Delivery:** quiet hours hold it; at most `Duel:PerDay` (2) sent; an unanswered duel is not repeated. New callback `d:{duel id}:{a|b|s}`
  (short id, well under 64 bytes); `ItemIdOf` returns null for it, so replies to a duel message are ignored with the help text.
- Expect ~14 votes a week from ten seconds a day. Config: `Duel:Enabled` (default true when Telegram works), `Times`, `PerDay`.

## F2. Shipped-it
When the issue behind a 💡 reaches done or cancelled, the source item's vote is re-weighted: done → weight 3, cancelled → weight 0.5
(applied once; stored in `ideas.outcome` and `outcome_at`, migration 0013).
- `IIdeaSink` gains `OutcomeAsync(Idea)` returning `Shipped | Dropped | Open | Unknown`. `PlaneIdeaSink`: new `PlaneClient.IssueStateAsync(project,
  issueId)` reading the work item's state group (`completed`/`cancelled`). `LocalIdeaSink`: always Open; `/ui/ideas` gets "mark shipped" and
  "drop" buttons (POST, CSRF) so local ideas close the same loop.
- Job `idea-outcomes`, daily 04:00 (a `ScheduledJob`), checks ideas with outcome null and age < 180 days. A vote that was manually changed
  after the idea was filed is left alone (compare `votes.at` with `ideas.at`).
- **Spike S1 (before coding):** the id from `intake-issues/` may be an intake record, not a work item; confirm on the owner's Plane (read-only)
  whether `work-items/{id}` resolves it and whether its state moves to a completed group once accepted and done. If it does not, `PlaneIdeaSink`
  matches by title/`description_html` marker (`feed-eater item {id}` is already written into the description, `IdeaFiler.cs`). Record the answer in
  this spec.
- Weekly review gains a line: ideas shipped, dropped, open.

## F3. Backlog bloodhound
Your open issues become a second memory: an item that matches one is annotated.
- **Source:** `IssueSource` interface, first provider Plane (all projects in `FeedEater:Plane`'s workspace, states in backlog/unstarted/started).
  GitHub Issues is a second provider later (needs a token); the interface carries `Ref`, `Project`, `Title`, `Text`, `Url`, `UpdatedAt`.
- **Index:** table `issues(ref pk, source, project, title, text, url, state_group, embedding vector(1536), updated_at, seen_at)`, refreshed daily at
  03:30 after profiles, embedding only issues whose text changed (hash). `PlaneClient` reads `description_html` (stripped to text) and pages past
  100. Closed issues are dropped from the table.
- **Match:** after a digest's read step, for each item shown take the nearest open issue by cosine; at or above `Backlog:Threshold` (default
  0.45, **calibrate on the real data first** like the cluster threshold: the implementer prints the distribution for 50 voted items and
  picks a value), the small model answers `{match: yes|no, why}` in at most 15 words (new prompt, fenced untrusted text, `LlmJson` parser).
- **Output:** the digest card gains "↳ may help LAB-42 · <why>". If `Backlog:Comment` is true (default false), also one Plane comment per
  (item, issue) pair with the link and the why (needs `PlaneClient.CommentAsync`; **Spike S2:** confirm the endpoint on the owner's Plane
  with a throwaway issue, nothing else). Pairs are stored in `issue_links` so nothing repeats.
- Off when Plane is off. Cost: one embedding per changed issue, one small-model call per shown item with a candidate.

## F4. Follow this story
A 🧵 button on a digest item follows its story for 14 days.
- **Table** `follows(id, root_item_id, started_at, ends_at, root_message_id, last_item_id, status active|closed, sent int)`; callback `f:{item id}`;
  at most 5 active follows and 50 messages per follow.
- `TelegramClient.SendAsync` gains an optional `replyToMessageId`. The follow's root is a short message "Following <title> for 14 days"; every
  later message about the story is sent as a reply to it, so Telegram groups them as a thread.
- **Matching:** a `FollowJob` (every 10 minutes, quiet hours hold) takes active follows and finds new items whose cluster head is the root's
  story (`items.cluster_of`), plus unclustered items with cosine >= `Cluster:Threshold` - 0.04 to the root or to any item already sent, within the
  window. Each goes out as one reply: title, link, one line "what's new" from the item's read or the first 200 characters, same 👍/👎 buttons.
- **Close:** at `ends_at` or `/unfollow`, one reply with a 3-sentence summary (read model, titles and summaries of up to 12 members) and the list
  of links. Follow replies carry item buttons, so replying to one acts on that item; replying to the root is ignored with the help text.
- `/follows` lists active ones with a stop button.

## F5. Hype autopsy
Ninety days after a 👍, check what the project did.
- **Snapshot:** table `repo_snapshots(item_id pk, repo, taken_at, stars, pushed_at, release_tag, created_at)`; a daily job (05:00) snapshots the
  repo of every 👍 item that has none, using `GitHubRepos.Find`. Optional `GitHub:Token` (new setting, secret) lifts the 60/hour limit; without it
  the job stops at 40 requests a run and carries on the next day.
- **Autopsy:** monthly job (1st, 09:00): for 👍 items whose snapshot is 87 to 93 days old, fetch the facts again and compute: stars growth %,
  pushed in the last 30 days, new releases (tag changed), idea filed and its outcome, saved to Karakeep, and later items from other sources about
  the same repo (cluster or cosine >= 0.84). Verdict per item: `grew`, `alive`, `quiet`, `gone` (404/archived).
- **Score:** share of 👍 items per verdict, split by the model's original relevance (3 vs 2) and by feed, so the report answers "was relevance 3 right
  more often than 2?" and "which feeds produce items that last?". Items without a repo are counted, not scored.
- Stored in `autopsy(month pk, built_at, report jsonb, message)`, shown at `/ui/autopsy` (same pattern as `/ui/weekly`), summary to Telegram. No model calls.

## F6. Taste map
`/ui/map`: every voted item and a sample of up to 1500 recent archive items as points on a plane, as one inline `<svg>` (no script).
- **Projection:** PCA by power iteration (top 2 components, 40 iterations) on the unit-length embeddings of the point set, cached 10 minutes. No new
  dependency. Axes are unlabeled; each profile key is drawn as a text label at the mean of its nearest points.
- **Encoding:** 👍 green, 👎 red (also different shapes: circle and cross, so colour is not the only cue), unvoted grey. Size by weight. Cells of a
  16 x 16 grid with archive items but no item ever shown in a digest get an outline: the regions the ranking never brings you.
- **Time-lapse:** `?month=YYYY-MM` links (server-rendered) show only votes up to the end of that month, with the strip of months above the plot.
- **Safety:** all text through `E()`, numbers formatted invariant, no inline style (use `fill`/`stroke` attributes and classes from `app.css`);
  fits the existing CSP.

## Built differently from this spec (wave 1, 2026-10-06)
- **W:** `SetVoteAsync(itemId, value, ct, weight = 1)` (ct is required and last). `FeedVotes.Up/Down` are doubles, so `Taste.MinFeedVotes` counts
  weight; the 100/10 learning floors still count rows. An idea-only item weighs 1; an item with a vote uses the vote's weight.
- **F1 Duel:** `Duel:Times` is a comma-separated string (the config binder appends to list defaults). With 7 eligible items the 40 to 60 band holds
  one, so the picker uses the two middle ranks. "Not offered again" means the pair; a skipped item can appear in a new pair. A reply to a duel
  message names no item, so it is an ordinary search or question and votes on nothing.
- **F4 Follow:** extra table `follow_items` records what was sent; matching needs `ingested_at` inside the follow window and a clustered item and skips
  muted feeds; a follow sends what arrived since the last run before closing; the 🧵 button is omitted on items whose story is already followed.
- **F5 Autopsy:** scores every snapshot at least 87 days old that no earlier autopsy scored (column `repo_snapshots.autopsy_month`), dropping snapshots
  still unscored after 180 days, instead of only the 87 to 93 day window; `autopsy.sent_at` retries a failed send; a snapshot costs up to two requests,
  so the 40-request cap covers about 20 repos a day without `GitHub:Token`; a 0-star baseline counts as 1. The idea outcome is a seam (`IdeaOutcome.None|Filed`)
  until F2 lands.
- **F6 Map:** axes are fitted on at most 1000 evenly spaced points (every point is still projected) with SIMD and fixed-block sums for speed; the
  time-lapse uses each vote's last-changed time and current weight because votes keep no history.
- **Not built yet:** F2 Shipped-it (migration 0013) and F3 Backlog bloodhound (migration 0017). Both wait for the two Plane spikes (S1 read-only,
  S2 writes one throwaway issue and comment in the owner's Plane and needs the owner's yes).

## Acceptance
1. Votes: a Duel tap writes the right votes and weights; Shipped-it re-weights once; a manual vote afterwards wins; `LearnedTaste` floors count rows.
2. Each feature has a test for its off state, its normal path, and its failure path (Plane down, GitHub 403/404/rate limit, model failure, Telegram
   failure), plus the hostile-content encoding test for every new page and Telegram message.
3. Quiet hours hold Duel and Follow; nothing new sends while quiet.
4. Full suite green; a smoke run with the example compose file and stubbed services shows each new page rendering.
5. Owner deploy: homelab-gitops PR adds `FeedEater__GitHub__Token` only if the owner wants it (secret via `secret.sh`), nothing else is required.
